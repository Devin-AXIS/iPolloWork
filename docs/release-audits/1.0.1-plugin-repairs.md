# iPollo 1.0.1 plugin repairs

Release packaging resumed after the repaired macOS application passed the checks below; publishing remains gated by final platform artifacts.

## Voice input

The installed desktop uses `~/Library/Application Support/iPolloWork Desktop/harness`, while the existing valid SenseVoice model files were stored under `~/.dsh/speech-to-text/sensevoice`. The same installed provider reported standby against the shared cache and unprepared against the desktop cache. All three source files match the official byte counts and SHA-256 digests. Desktop startup now copies only missing, verified model files into its own cache without replacing any existing file. Two independent worker processes each reused the restored cache and transcribed the same sample twice without downloading models.

## Computer use

The installed provider archive contained no `native/bin` helper. The enable operation was recorded as failed. Packaging now requires both signed and notarized macOS helper architectures before packing the provider; missing payloads fail the build. Helpers are built from unchanged pinned official sources in the ignored desktop build directory. Both native helper protocol, identity and cleanup checks passed. A real provider transport test returned macOS permission state. Windows packaging also builds the pinned .NET 10 helper in an isolated cache and unpacks its complete self-contained runtime. The official PTC permission/runtime and agent-scope regression tests passed (69 cases). This does not grant Accessibility or Screen Recording permission automatically.

## Remaining acceptance

The signed ARM application ASAR contains both helper receipts with valid notarization tickets. Its provider reaches running state; the PTC row reads 已设为持久化 and the permission controls load without the old errors. The repaired ASAR also transcribed the same audio twice using the existing models. Final release archives and Windows execution still require validation before publishing v1.0.1. Direct inspection of the running 1.0 UI confirmed “无法读取 PTC 执行方式，请在设置中检查”, inactive cuaAccess endpoints and the backend error identifying the missing signed helper in the mounted 1.0 application. This ties the PTC status failure to provider activation; final 1.0.1 UI acceptance is still required.
