# iPolloWork 交互规范

> 本文是产品、设计、研发和测试共同使用的交互约束，适用于桌面端与共享 Web 界面。它规定新功能应采用的做法，也用于现有界面的渐进式收敛。当前产品行为见 [`client-interactions.zh-CN.md`](./client-interactions.zh-CN.md)。最近核对：2026-10-08。

## 1. 基本原则

1. **同一种意图使用同一种交互。** 视觉可以随密度和场景调整，但控件语义、状态反馈、确认时机和键盘行为不能因页面而异。
2. **状态就在操作发生处反馈。** 表单错误跟随字段，保存状态靠近保存入口，预览错误留在预览区域，任务状态出现在任务入口和任务详情内。
3. **系统完成与用户确认分开。** 请求成功、文件保存、Agent 回答结束、交付结果验收是四件事，不能都用“完成”表示。
4. **先保留用户输入，再处理失败。** 异步失败不能清空表单、选择、草稿或当前预览；应给出原因和就地重试入口。
5. **非技术用户不需要理解内部状态。** 文案说明“正在做什么、是否需要我处理、下一步是什么”，内部引擎名和状态码只放在诊断详情中。
6. **不只靠颜色表达状态。** 状态至少同时使用文字，并在空间允许时配合图标；紧凑入口也必须提供可访问名称。

## 2. 现状核对与统一结论

本次核对覆盖 `apps/app/src/components/ui`、`apps/app/src/react-app/design-system`，以及会话、工作台、设置和任务中心中的实际调用。

| 范围 | 现有做法 | 已确认的统一做法 | 对应组件 |
| --- | --- | --- | --- |
| 表单 | `Field + Input`、旧 `TextInput`、业务页原生控件并存 | 业务表单以 `Field` 组合字段结构，以共享输入组件承载控件状态；原生控件只保留文件、颜色、画布属性等特殊输入 | `Field`、`FieldLabel`、`FieldDescription`、`FieldError`、`Input`、`Textarea`、`Checkbox`、`RadioGroup`、`Switch` |
| 单选选择器 | Base UI `Select` 与手写 `SelectMenu` 并存 | 统一使用 `Select`；搜索型选择使用 `Autocomplete`；少量可比较选项直接使用 `RadioGroup` | `Select`、`Autocomplete`、`RadioGroup` |
| 预览 | 右侧工作台、弹窗、卡片封面和整页遮罩分别处理加载与失败 | 预览入口、承载位置可以不同，但统一使用“加载中 / 空 / 可用 / 失败”四态和同一套恢复规则 | `Dialog`、`Skeleton`、`Empty`、`Alert`、`Button`、`Progress` |
| 任务状态 | 边栏圆点、旋转图标、看板徽标、正文状态文案各自映射 | 执行状态与工作项状态分层；同一状态使用一致的名称、图标语义和色彩含义 | `Badge`、`Progress`、`Skeleton`、会话 `SessionStatusIndicator` |
| 结果确认 | Toast、保存状态、确认弹窗和“验收完成”都可能被理解为完成 | Toast 只确认操作；交付物使用持久的待验收区域；破坏性操作使用统一确认弹窗 | `ConfirmModal`、`AlertDialog`、`ConversationWorkspace` 的验收区、`toast` |

现有实现中需要收敛的代表性位置：

- `react-app/design-system/text-input.tsx` 与 `components/ui/field.tsx`、`input.tsx` 重复定义了字段外观和标签结构。
- `react-app/design-system/select-menu.tsx` 手写了弹层、选项和关闭行为，而 `components/ui/select.tsx` 已提供 Base UI 的键盘、焦点和定位能力。
- `question-modal.tsx`、`skills-view.tsx`、`workspace-app-frame.tsx` 等仍有自行绘制的常规输入控件；设计属性、文件和颜色输入属于可以保留的专用场景。
- 模板卸载、Design 未保存跳转、提供商密钥删除和 Control Mode 授权仍有 `window.confirm`，与 `ConfirmModal` 并存。
- 任务边栏、任务看板和项目概览分别维护状态表现，含义接近但标签和颜色并不完全一致。
- 模板、图片、Design、文件和视频预览已有各自容器，但加载、空态、失败和重试的位置不同。

## 3. 表单

### 3.1 字段结构

普通字段按以下顺序组合：

```text
Field
  ├─ FieldLabel              必填，除非控件有同等清晰的可访问名称
  ├─ Input / Textarea / ...  输入控件
  ├─ FieldDescription        可选，提交前也有帮助的说明
  └─ FieldError              校验失败时显示
```

- 标签描述“填写什么”，占位符只给格式示例，不能代替标签。
- 必填、格式限制和用途等稳定说明放在 `FieldDescription`；具体错误放在 `FieldError`。
- 错误出现后，为控件设置 `aria-invalid`，错误信息使用 `FieldError` 的 `role="alert"`。
- 同一表单的字段间距由 `FieldGroup` 管理，不在每个业务页面重新拼间距。
- 多行正文使用 `Textarea`；搜索、命令输入和画布数值等专用输入可以使用自己的紧凑布局，但仍须保留焦点、错误和禁用语义。

### 3.2 校验与提交

- 初次进入页面时不显示错误。字段失焦后可校验当前字段；提交时校验全部字段，并把焦点移到第一个错误。
- 能在客户端确定的问题就地提示；服务端错误保留用户输入，并在表单顶部或对应字段显示原因。
- 提交期间禁用重复提交，主按钮显示旋转图标和动作进行态，例如“正在保存”；不要只把按钮文案改成笼统的“处理中”。
- 成功后再关闭弹窗或侧栏。失败时保持当前容器、滚动位置和输入内容。
- 自动保存不得使用 Toast 反复打扰。状态固定显示在编辑区标题栏：`未保存 → 正在保存 → 已保存`；失败时显示“保存失败”和“重试”。`ArtifactPanel` 的 `saveStatus` 是现有参考。

### 3.3 表单容器

| 场景 | 容器 | 规则 |
| --- | --- | --- |
| 页面内设置 | 页面或卡片 | 修改范围清楚时可即时保存；否则在区块底部提供“取消 / 保存” |
| 简短命名、连接或配置 | `Dialog` | 默认聚焦第一个可编辑字段，`Enter` 提交，`Esc` 关闭；有未保存内容时先确认 |
| 较长且需要上下文的编辑 | `Sheet` 或独立页面 | 操作栏保持可见，关闭前检查未保存内容 |
| 破坏性确认 | `ConfirmModal` | 不在普通表单底部临时拼第二套确认区 |

`RenameSessionModal` 中的 `Field + Input + Dialog` 组合可作为简短表单参考。

## 4. 选择器

### 4.1 控件选择

| 用户任务 | 使用组件 | 适用条件 |
| --- | --- | --- |
| 从列表中选一个 | `Select` | 默认选择器，选项数量不多且不需要搜索 |
| 从较长列表中查找一个 | `Autocomplete` | 通常超过 10 项，或用户更可能按名称搜索 |
| 比较后选一个 | `RadioGroup` | 2–5 项，且每项需要同时展示解释或影响 |
| 选择多个独立选项 | `Checkbox` / 复选列表 | 每项可以独立启用；必须显示已选状态和数量 |
| 打开或关闭一项即时设置 | `Switch` | 切换后立即生效，不需要再点“保存” |
| 工具栏中的互斥模式 | `ToggleGroup` | 图标或短标签，当前模式持续可见 |

### 4.2 统一行为

- 新代码不再使用 `SelectMenu` 或为常规单选手写 `button + listbox`。
- 设置页需要紧凑外观时，使用 `SelectStyleScopeProvider value="settings"`，不复制一套选择器。
- 触发器必须显示当前值；没有值时显示明确占位，不使用空白或仅用图标表示。
- 选项变更若立即生效，选择后关闭弹层并在原位置更新；若属于表单草稿，只更新草稿，提交后才生效。
- 选项需要长描述时改用 `RadioGroup` 或选择卡，不把多行解释塞进普通下拉菜单。
- 不可用选项保持可见并说明原因；只有对所有用户都没有意义的选项才隐藏。

## 5. 预览

### 5.1 预览层级

| 层级 | 用途 | 现有承载 |
| --- | --- | --- |
| 缩略图 | 快速识别内容，不承担检查细节 | 模板卡片、产物卡片、媒体列表 |
| 临时大图 | 放大查看单个模板或媒体，关闭后回到原位置 | `Dialog`；模板预览、`workspace-app-frame` 图片预览 |
| 持续工作预览 | 与对话或编辑并行，支持保存、导出、刷新和切换产物 | 右侧 `SidePanel`、`ArtifactPanel`、Design / Video 面板 |

点击缩略图只负责打开预览。安装、使用、导出等主动作必须有独立文字按钮，避免用户误触后直接改变数据。

### 5.2 四种状态

每个预览面都必须覆盖以下状态，状态切换不得改变容器尺寸：

| 状态 | 展示 | 行为 |
| --- | --- | --- |
| 加载中 | 与最终结构接近的 `Skeleton`；有可信百分比时使用 `Progress` | 保留标题和关闭入口，不显示空白白屏 |
| 空 | `Empty`，说明为什么没有内容 | 若能恢复，提供一个主要动作，例如“选择文件”或“重新生成” |
| 可用 | 内容、名称和必要的查看工具 | 刷新时优先保留上一份可用预览，并显示轻量更新状态 |
| 失败 | 预览区域内的 `Alert` 或同等错误面 | 显示用户可理解的原因和“重试”；诊断详情默认折叠 |

预览失败不使用一次性 Toast 作为唯一反馈，因为 Toast 消失后用户仍面对不可用的区域。`SidePanel` 的 Design 错误边界和 `VideoPanel` 的启动失败面都已有就地重试，可统一到上述结构。

### 5.3 标题栏与未保存内容

- 持续预览的标题栏从左到右为：类型或文件图标、名称、保存或同步状态、查看工具、主要动作。
- “预览”“编辑”是模式切换时，要明确显示当前模式；不要让同一个按钮既表示当前状态又表示下一步动作。
- 关闭或切换会丢失草稿时，使用 `ConfirmModal`，并明确写出会丢失什么；不能使用浏览器原生确认框。
- 导出或生成开始后，在预览内持续显示进度。成功可以补充 Toast，但预览内仍应留下可打开或下载的结果。

## 6. 任务状态

### 6.1 两层状态模型

执行状态回答“Agent 或后台任务现在发生了什么”，工作项状态回答“这项工作走到哪一步”。两者不能用同一个字段互相推断。

| 层级 | 标准状态 | 用户文案 | 视觉与动作 |
| --- | --- | --- | --- |
| 执行 | idle | 空闲 | 通常不显示 |
| 执行 | queued | 等待开始 | 中性图标或文字；允许取消时提供取消 |
| 执行 | running | 正在执行 | 旋转图标；有真实进度时才显示百分比 |
| 执行 | waiting | 等待你处理 | 蓝色提示、明确所需输入或授权，并把任务入口标为待处理 |
| 执行 | retrying | 正在重试 | 说明重试原因；保留停止入口 |
| 执行 | failed | 执行失败 | 红色图标、原因和重试或更换方案 |
| 执行 | completed | 执行已结束 | 不直接显示为“验收完成”；有交付物时进入工作项的待验收状态 |
| 工作项 | planned / ready | 计划中 / 待开始 | 中性状态 |
| 工作项 | running | 进行中 | 强调当前活动 |
| 工作项 | review | 待验收 | 明确提示用户检查交付结果 |
| 工作项 | done | 已验收 | 绿色完成态，表示用户已经确认 |
| 工作项 | failed | 失败 | 保留原因和恢复入口 |

### 6.2 不同密度下的表达

- 边栏等紧凑位置可以只显示圆点或图标，但必须带 `aria-label` / `title`；现有 `SessionStatusIndicator` 是参考入口。
- 列表、卡片和看板使用 `Badge` 或图标加文字。相同状态不因页面不同而改变颜色含义。
- 详情页用完整文字说明状态和下一步；等待用户时将所需操作放在状态旁边。
- `Progress` 只显示真实、单调递增的进度。无法估算时使用旋转图标或步骤文案，不显示伪百分比。
- 加载数据使用 `Skeleton`；任务运行使用状态组件。二者不能互换。

现有 `getSessionActivityStatusLabel`、`SessionStatusIndicator` 与 Work 看板的 `executionStatus` 应作为后续合并状态映射的起点，不再由业务页面新增第三套近义状态表。

## 7. 结果确认与反馈

### 7.1 先判断用户要确认什么

| 类型 | 示例 | 反馈方式 |
| --- | --- | --- |
| 操作成功 | 已复制、已保存、已安装 | 简短 Toast；若结果仍在当前页面，也可以只更新原位置状态 |
| 可恢复问题 | 保存失败、预览加载失败、连接中断 | 问题所在区域的 `Alert` + 重试；必要时补充 Toast |
| 需要用户作决定 | 权限申请、覆盖文件、丢弃草稿 | `AlertDialog` / `ConfirmModal`，等待明确选择 |
| 交付结果验收 | Agent 已交付文件、任务达到完成条件 | 持久的“待验收”区域，展示检查提示和“验收完成”按钮 |
| 破坏性操作 | 删除、卸载、覆盖不可恢复内容 | `ConfirmModal variant="danger"`，按钮使用具体动词 |

### 7.2 交付验收

`ConversationWorkspace` 现有的 `review → done` 流程是标准参考：Agent 回答结束后进入“待验收”，用户检查交付物并点击“验收完成”后才进入 `done`。

- 验收入口必须持续可见，不能只出现一次 Toast。
- 提示中说明要检查的对象，优先提供“打开结果”或“查看产物”，再提供“验收完成”。
- 验收按钮只改变验收状态，不顺带关闭、归档或删除任务。
- 提交验收时按钮进入加载态；失败后仍保持待验收，并在原位置显示原因。
- 已验收状态保留简短记录；如支持撤销，应明确撤销只改变验收状态，不回滚文件。

### 7.3 确认弹窗

- 统一复用 `ConfirmModal`；权限等需要展示范围和元数据的复杂决策可以直接组合 `AlertDialog`。
- 标题写具体后果，例如“删除这个任务？”；确认按钮写具体动作，例如“删除任务”，不使用“确定”。
- 取消按钮描述安全出口，例如“继续编辑”“返回任务”；普通场景可用“取消”。
- 破坏性主按钮使用 `destructive`，默认聚焦安全动作。执行期间禁用重复点击，弹窗在成功后关闭；若操作失败，需要保留或恢复上下文并显示错误。
- 禁止新增 `window.confirm`。现有调用应逐步迁移到 `ConfirmModal`。

### 7.4 Toast 的边界

Alert 与 Toast 统一使用无边框、无投影的语义浅背景；信息、成功、警告、错误沿用共享反馈背景 Token，对应 sky/green/amber/red 第2档，暗色主题采用低亮度底色。保留状态图标和文字，不能只靠颜色说明问题。关闭和恢复动作保持可访问；不将此规则套到表单错误边框或确认弹窗。

普通操作按钮默认32px，设置作用域28px；选中不得改变字号、行高、尺寸或 padding。装饰伪元素绝对定位，不占 flex 间距。DialogContent 关闭入口统一为 ghost、28px点击区、16px居中图标，保留键盘焦点提示和 Escape 焦点恢复；页面不得另写偏移和缩放。

- Toast 适合不阻塞后续操作、无需用户记忆的短反馈。
- Toast 不承担字段错误、长期任务状态、预览失败、待处理权限或交付验收。
- 同一事件默认只反馈一次。页面已经明确显示“已保存”时，不再弹“保存成功”。
- 错误文案包含可执行的下一步；内部错误信息可放在 description 或可展开详情中。

### 7.5 颜色与字体

客户端和插件沿用共享视觉Token，不按页面重新定义颜色与字号。以用户2026-10-10提供的七档紧凑UI字体表和Teal品牌色板为设计目标；颜色用途、字体栈、字号/行高、字重、根字号、真实调用入口及现状差异统一维护在 [插件接入契约 · 主题与 Token](../.codex/skills/ipollowork-plugin-ui/references/plugin-contract.md#主题与-token)，避免交互文档复制数值形成第二个来源。品牌展示大字号不套入客户端操作页。

普通正文、卡片与浮层分别使用对应的前景/背景组合；反馈使用语义浅背景。标题、控件、正文、说明和元数据有不同层级，选中/hover/主题切换不改变文字几何。共享组件先沿用默认排版，不从父页面复制样式覆盖。页面级迁移需验证中英文、长文案、亮暗、窄窗口和实际缩放；界面规范不改变作品配色或字体。已有短片页面字体、设置专用颜色及完整Figma文字样式对照仍需分别收敛，不能声明全客户端视觉已统一。

## 9. 新功能检查表

提交设计或实现前，逐项确认：

- 是否复用了现有组件，而不是重新组合常规输入、下拉或确认弹窗？
- 字段是否有标签、说明、错误、禁用和提交中状态？失败后输入是否仍在？
- 选择器类型是否符合选项数量、搜索需求和单选 / 多选语义？
- 预览是否覆盖加载、空、可用和失败四态，并能在原位置恢复？
- 页面显示的是执行状态还是工作项状态？“执行结束”是否被误写成“验收完成”？
- 用户是否清楚当前需要做什么，以及下一步会发生什么？
- 反馈是否放在正确层级，而不是所有结果都依赖 Toast？
- 破坏性操作是否使用统一弹窗、具体动作名和安全默认焦点？
- 键盘焦点、可访问名称、错误播报和颜色之外的状态线索是否完整？
- 颜色是否来自共享语义 Token，文字是否采用已定义的层级；是否核对实际根字号、运行时样式生成及缩放，而不是只检查控件外框？

## 10. 现有界面的收敛顺序

1. **停止新增分叉。** 新表单、选择器和确认交互直接遵守本文，不再引入同类封装。
2. **先处理高风险差异。** 将 `window.confirm` 迁移到 `ConfirmModal`，将常规用途的 `SelectMenu` 迁移到 `Select`。
3. **统一字段组合。** 逐步用 `Field` 系列替换旧 `TextInput` 和业务页常规原生输入；专用画布、颜色和文件控件保留例外。
4. **收敛状态映射。** 让会话边栏、任务看板和项目概览共享同一份状态语义，表现层再按密度选择图标、Badge 或完整说明。
5. **统一预览壳层。** 在不改变各工作台能力的前提下，复用四态、标题栏和恢复动作；具体实现前先按仓库流程确认演示脚本。
