# 桌面启动失败与官网下载修复说明

日期：2026 年 11 月 20 日。

## 启动失败的原因

提供的诊断报告对应 iPollo 1.0.7、macOS ARM64，启动位置为 1.0.7 的 DMG 挂载卷。

报告中的模型核心 `@deepseek-ai/dsh-llm` 实际版本为 `0.2.0-rc.1`，其他应用组件为 `0.2.2-rc.3`。调用栈显示：

- `dsh-llm` 和 `dsh-typert-protocol` 从用户 profile 的 `node_modules` 加载。
- Cordis 等应用运行时从安装包内的 `app.asar` 加载。
- 原始异常为 `cannot get property "root" without inject`。
- LLM 服务初始化失败后，必需的 Agent loop 和会话控制器等组件无法获得服务，最终使 Host 启动中止。

应用安装目录与用户目录分开。升级应用会替换安装包中的代码，但保留用户已安装的插件、依赖和配置。本次启动的模块解析允许用户目录中的同名旧核心包覆盖应用携带的版本，而升级过程此前没有排除这类冲突，导致新旧模块混用。

正常预期应当是使用应用自带的匹配核心版本。现有报告包含插件安装记录，但不足以确定哪一次安装引入了旧依赖，因此不能将来源归因于某个具体插件。该错误也不是 API Key 校验失败。

## 修复方式

修复版在现有 profile 锁内、Host 启动之前，按应用运行时清单检查已知 DSH/Cordis 核心包版本。发现冲突时，将 profile 中的旧核心条目移入独立的 `runtime-dependency-backups` 备份目录，并写入 `repair.json` 记录，再继续通过官方加载器启动。

修复保留账号、Key、会话、项目文件、插件包和配置；不会要求用户清空整个用户目录，也不会在启动时运行包管理器。每次启动均执行校验，以处理后续插件安装重新带入旧核心包的情况。无关插件和版本一致的核心副本保持原样。

原报错弹窗只保留末尾内容，隐藏了根因。修复后保留开头的失败组件和异常，同时仍可获取完整诊断报告。

## 验证范围

回归检查覆盖旧核心包备份、重复启动、插件及用户数据保留、错误摘要和下载别名。真实 Host 检查预置旧版核心包，确认修复后能够启动。

Mac ARM 修复包还通过了两轮完整 Host/Office 检查、签名、公证和 Gatekeeper 校验；从完成的 DMG 复制应用后，实际欢迎窗口能够打开，旧核心备份记录为 `complete`。这属于测试 Mac 上的安装验证，并非已经操作了报告来源的那台 Mac。

Intel 首次 CI 恢复发生 LibreOffice 的 XLSX 操作超时，具体机制尚未确定。同一份签名应用在新宿主连续两轮通过完整 Host/Office 检查，随后通过公证、Gatekeeper 和 DMG 安装后实际窗口及旧核心修复验证。未修改应用、扩大签名权限、放宽超时或跳过检查；这一对照也不能视为已经确定了先前超时的原因。

## 官网下载问题

原官网能够匹配带 `unsigned` 的 Windows 文件名，但依赖未认证的 GitHub Latest API 在五秒内成功响应。诊断时该 API 返回 403，原回退行为因此跳转 Release 页面；文件名不是唯一原因。

修复后，支持的平台先获得固定安装文件直链，API 成功时再采用精确版本地址。发布流程提供规范的 `ipollowork-win-x64-<version>.exe` 和各平台固定 `latest` 文件名，均复制自摘要验证过的原始安装包；保留自动更新器原有的文件名与内容。

国内官网与国际官网均已部署此下载修复，并已在真实浏览器中确认 Windows 下载按钮指向安装文件直链。
