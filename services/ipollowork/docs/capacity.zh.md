# 百人内测容量与运行边界

员工各自在电脑上运行 Electron 和 Agent；ECS 负责账号、组织、项目、模型与 MCP 转发、OSS 文件接口和发布。2 核 4G 的规划不包括在这台机器运行一百个 Agent、本地模型或视频渲染。

服务分别允许 32 个普通接口、2 个密码操作、8 个模型/能力调用、4 个文件传输和 128 个 MCP 传输并发；每组最多排队 160 个请求。普通接口最多等 5 秒，密码操作 20 秒，模型与文件传输 120 秒。超过容量或等待时间，返回明确的 `503` 和 `Retry-After`，不会无限累积内存。排队时不扣积分、不提交模型任务；取消排队后不再执行。无法确认结果的付费调用不会自动重试，以免重复消费。

`/api/health` 检查进程存活，`/api/ready` 检查数据库和停机状态。平台管理员可调用 `/api/v1/admin/runtime` 查看队列、内存、事件循环及数据库连接数，不返回密钥或请求正文。请配置站外可用性、内存、磁盘、数据库和排队告警。单台 ECS 和同机数据库仍有单点故障风险，需要外部备份和恢复演练。

使用独立测试数据库设置 `TEST_DATABASE_URL` 后运行 `npm run bench:http`。脚本自行创建并删除随机命名的隔离 schema，用真实 HTTP 服务、120 个合成账号和本地模拟模型上游验证。2026 年 11 月 19 日的 Windows 测试中，120 个同出口并发登录、360 次鉴权查询、120 次模型调用和重复请求重放均成功，没有重复扣费。登录耗时 5.469 秒，查询 1.797 秒，模型阶段 6.353 秒；模型最大并发 8、最多排队 112、服务进程 RSS 峰值 256 MiB、存活检查 P95 为 7 毫秒。子进程 V8 堆限制为 768 MiB，模拟上游每次延迟 350 毫秒。宿主为 4 物理核、16 GB、PostgreSQL 18。这证明排队等功能在该测试负载下有效，尚不能作为 2 核 4G Linux 真机、真实供应商额度或长时间稳定性的达标证明。

新建 2 核 4G 内测机器可试用[容量配置](../deploy/compose.beta-2c4g.yml)：Work 限制 1536 MiB、PostgreSQL 768 MiB、Caddy 128 MiB，主库连接池 8、应用数据池 4。上线前在目标规格复测相同镜像、代理、OSS 地域和实际业务；现有 4 核 8G 建议先保留。准备同地域私有 OSS、异机数据库备份、恢复演练、磁盘与可用性告警，并确认模型供应商 RPM、TPM 与并发额度。媒体访问可通过 OSS/CDN 分流；一百个账号不意味着当前公网带宽能承载一百人同时下载视频。镜像构建放在 CI 或独立构建机执行。
