# App data

App data lets plugins, websites, apps and mini programs built in DSH keep records in the signed-in iPolloWork account. The account service stores them in a separate database and accepts only JSON statements; see [the service reference](../../../services/ipollowork/docs/app-data.md) for limits, permissions and the statement format.

## Data page

The sidebar's Data entry opens one tab for personal apps and one per organization the account belongs to, including organizations without apps. Filters show all apps, plugins or public apps by the kind each app declared when it was created. Each app is one compact row: its mark, name, record count, creation date and kind; the row's tooltip names the workspace it was created in. Opening an app shows its records first: one tab per table over a grid with row numbers, fifty records to a page. A search box finds records whose id or any text or number field contains the term; Filter adds conditions per field (contains, is, is not, comparisons for numbers, is empty), which all must hold. Column headings sort by that field. A row opens a side sheet with every field of the record; any member of the app's owner can change values, delete the record after a second confirmation, or add a record with New record. An edit sends only the changed fields with the record's version, so a newer change made elsewhere is reported instead of overwritten. The page never adds, renames or removes fields: those come from the plugin, the page code or the model. The endpoint, public key and sign-in address of a public app stay behind the Connect control. The More menu, for managers, lists the app's administrators, who are added by iPollo account email and may change every record from the app's own page, and deletes the app. An app the platform operator suspended is marked in the list and explains on its page that nothing can read or write it until it is resumed.

## Model

The `app_data` tool takes an app name, its kind (`plugin` or `site`), an optional organization and one statement. The first write with a name creates the app with that kind and records the current workspace's title; later calls reopen it, matching the name without regard to letter case. The Host remembers which app a name opened for five minutes per signed-in account, so repeated calls send only the statement; a statement that finds its app deleted resolves the name again. A read of an unknown app creates nothing and fails with `DATA_APP_NOT_FOUND`, listing the owner's apps and their kinds. Reads may run concurrently; writes run in call order and fail with `IPW_DATA_READ_ONLY` in a session whose sandbox policy is read-only. Stopping the call cancels its account request, although a write the service already received may have committed. The tool result is the statement result, and `{"info":true}` lists collections, fields, the endpoint and the public key. A signed-out account fails with an instruction to ask the user to sign in. Rejections keep the service's explanation, which names the existing collections and fields, so the model can correct the statement.

The `app-data` runtime skill is the complete contract for the model: when to use app data, how page code calls it with a public key, and how a plugin's Host half and Client module call `ipolloData`. Cordis inspection catalogs only DSH's own services, so the skill, not inspection, is how the model discovers this service. The tool and skill are registered only when the account features are enabled.

## Plugins

The suite provides `ipolloData` on the Host and in the browser with one contract, `IpolloData` in `src/shared/app-data.ts`. A Host plugin injects it; a Client module lists `@ipollo/dsh-suite` in `dsh.client.inject` and injects it. `ctx.ipolloData.open(name, { organization })` creates or reopens the plugin app and returns `run(statement)` and `collection(name)`, whose `insert`, `get`, `find`, `count`, `aggregate`, `update`, `increment`, `upsert` and `delete` send the matching statements. A statement on an app that was deleted opens the app again and runs once more. Both services build the handle with `createDataApp`. The browser service calls the suite's same-origin routes and rejects with `AppDataError`, whose `code` is stable and whose message carries the service's explanation. Plugins hold no token or connection string.
