# HyperFrames Video Rules

Put whole-video settings in leading `---` frontmatter. Each shot field MUST be a separate list line beginning `- key: value`; never join metadata with semicolons, translate field keys, or write a Markdown pipe table. Omit unset optional lines entirely, never literal `omit` or `null`. Re-read the saved file to verify every shot has a non-empty `- scene:` and positive `- duration:` before reporting it ready.
Use for `video`, including template application, custom generation and targeted edits. The active session's exact project, runtime, media actions and editor contract are authoritative. In the [shared guidelines](template-generation-contract.md#ipollowork-shared-creative-and-layout-guidelines), consult only sections 2–3 for scope/content, section 5 for layout selection, and section 7 for media. Read [video-motion-principles.md](video-motion-principles.md) once for initial generation or substantial scene redesign. Read [video-acceptance.md](video-acceptance.md) once before final validation; targeted edits run only its affected checks plus core playback. Do not load unrelated category guidance.

## Plan content and reuse

Bound the script draft stage: read the source and inventory coverage once, choose one content-led shot sequence, then make one rough narration-duration estimate per shot (about 4 CJK characters or 2.5 Latin words per second, plus purposeful reading holds). Use a single counting calculation when needed; never repeatedly hand-count characters or compare near-identical narration versions to fit an approximate target. Approximate targets are not strict caps. Save the complete native STORYBOARD.md with status: outline and estimated positive durations as soon as coverage, spoken lines and concrete shot treatments are settled, before media capability discovery or production. Beat ranges in this draft are provisional scene-relative planning windows, not word alignment: do not calculate per-word, per-phrase or frame-accurate timestamps before synthesis. Combine the source/semantic and saved-format checks into one post-save review and repair observed defects together; reopen only affected shots when facts, user edits, a failed check or measured audio introduce new evidence. Preserve required facts and explicit user caps; an irreconcilable cap needs one consequential user choice, not deletion, accelerated speech or endless estimation. After approval, use measured audio and provider alignment to retime dependent beats; without alignment use honest sentence-level captions, never character-proportional word timestamps. This is an execution guideline, not a runtime timeout or a guarantee of model latency.

Before splitting shots, inventory the supplied source's important claims, steps, figures and qualifications. Keep a compact source coverage map in the existing frame narrative: point ID → source heading/page/paragraph → frame(s) → spoken or visibly explained evidence. Put intentional omissions and their reasons in the first frame's notes. For a brief without source files, trace requirements to shots instead; never invent source anchors. Preserve names, numbers, units, causal relationships and meaningful parentheses/qualifiers. Required points must be covered; an explicit duration cap that cannot fit them needs a user choice, not silent deletion or rushed narration.

Choose shots from audience takeaway → visible evidence/change → matching temporal pattern and layout → motivated camera treatment. Record the fit rationale in each frame's narrative. Keep process/technical steps readable with fixed framing and local reveals; compare before/after at matching viewpoints and scales; use spatial travel only when spatial relationships are the subject. A library match, cinematic preset or attractive stock clip is not proof of suitability. Decide readable holds before motion and keep illustrative media distinct from factual evidence.

Before script approval, re-read the source and saved storyboard: reconcile every required coverage point with actual narration/visible content, check shot fit and readable holds, and repair contradictions, missing qualifications or unsupported claims. List unresolved source gaps explicitly rather than reporting the script ready. This is agent semantic self-review, not a deterministic parser or rendered-quality verdict; do not claim a source check or audition that did not happen.

Bind each semantic narration beat to its exact spoken phrase, intended takeaway, visible subject/change, required asset or editable graphic, and readable result/hold in that frame's existing narrative. Keep beats in spoken order; one sentence may span beats, and adjacent phrases may share one beat. For search/import needs, write one concrete query per distinct visual need (subject + action + setting, with date/location when factual), optional English/local-language equivalent and exclusion criteria. Reuse identical needs across beats; no fixed keyword quota or whole-video generic keyword list. Verify source relevance, provenance and license before choosing footage. If a claim needs a diagram or exact data, use editable graphics instead of loosely related B-roll.

For a generated asset, derive asset_brief from subject/identity + environment + action/change + framing/camera + semantic timing + final state + style + needed sound; omit irrelevant parts and respect the selected model's actual capabilities and duration limits. Each supplied reference must have an explicit role: identity/product, setting, style, first/last state, motion or audio. Record exact project paths, what to preserve and what may change in frame notes. Resolve conflicting references from user priorities, asking only for consequential ambiguity. Maintain recurring subject appearance, product details, location geometry, palette and screen direction across connected shots. Do not copy a reference's factual claims or unwanted text, or invent @reference syntax, uploads or generated audio for a provider that does not support them.

Plan narration for natural speech: meaningful phrase boundaries, pronunciation of names/abbreviations/numbers, emphasis and purpose-led breath/reading pauses. Keep stage directions and pause markers out of voiceover spoken text; store them in frame notes. Apply only supported delivery controls consistent with the saved voice/user request; do not invent pauseSeconds or SSML support, override a pinned voice or add unrequested voice instructions. A visual hold is not an inserted audio pause. After synthesis, map captions, callouts and focus changes to real provider word timings and measured audio, preserving the timing sidecar. Without word alignment, use honest sentence-level captions, not evenly divided word timestamps. If exact audible pauses are required but unsupported, disclose the gap rather than claiming precise silence. Recheck transcript and all dependent beats/captions after narration edits.

Plan a genre-appropriate whole-video rhythm in the first frame's notes: hook/orientation, development/evidence, resolution or requested action, with relative energy and information density rather than fixed scene counts or percentages. Explain how each shot contributes. Technical/course material prioritizes dependency order and reading time; document/factual stories prioritize context and evidence; promotional reveals may use stronger contrast, while quiet stories need not end in a sales CTA. Each shot recipe records entry state, focal subject, content change, resolved state, readable hold, transition intent and relevant limits, using the existing temporal-pattern/component map. Vary rhythm at meaningful changes, not arbitrary camera switches; do not force fast travel, compulsory slow motion, once-per-preset quotas or music-beat cuts on every genre. Use real measured audio cues only when music-led timing is appropriate.

Read the brief, current `index.html`, template guide, tokens and existing assets. For initial/full generation, plan audience/message, narrative shots and visual beats, required media, actual assets, then timed HTML composition. Use a compact storyboard giving every scene a purpose, visible content, narration intent, media need and approximate duration. For every substantive scene, include the compact narration beat map defined in `video-motion-principles.md`; it binds each spoken intent to a time range, visual focus, visual action, and result or hold. Reference-file, course and technical-explainer requests stop after saving `STORYBOARD.md` for approval; explicit approval or an explicit request to skip review proceeds from that same script into production. Other finished-video requests proceed through the plan without an extra gate. A script-only request saves the script without generating media or changing the composition. Never repeat an already supplied confirmation. Content determines scene count and timing; sample counts and durations are not quotas. An explicit user maximum remains strict. For targeted edits, preserve unrelated scenes, media and user changes.

Use the existing Studio `STORYBOARD.md` as the durable script and shot plan, not a new JSON format or an additional planning document. Write the narrative first (message, audience, hook, development and payoff), then break it into shots. `theme: "ai-auto"` derives a creative direction from the brief while preserving current Work design tokens; a manually selected Work theme ID applies that design system. `visual_style` stores overall natural-language direction. `music_prompt` describes the full-video music direction; when empty, infer it from content and pacing. `music_asset` pins the actual project-relative audio file after sourcing, so a direction cannot be mistaken for a complete soundtrack.

Use native `## Frame N — Title` sections with `scene`, `duration`, `transition_in`, `status: outline`, `voiceover` (the spoken line), and optional `speaker` only when dialogue or character identity matters. Ordinary narration does not require a character name. Optional `voice_id`, `voice_model`, and `voice_name` select a library voice for that shot; `voice_id: auto` delegates a suitable authorized choice, while empty fields inherit the project default. Put per-shot production choices in metadata: `camera`, `asset_source` (`auto` delegates the decision; otherwise `existing`, `search`, or `generate`; `code` for editable graphics requiring no imported visual), `asset_kind` (`image` or `video`, omitted for AI choice), `asset_brief`, `asset_origin` (source URL/attribution or generated-illustration description), `asset_reference` (exact local project media path), `sound_effects` (event/time) and `sound_effect_reference` (exact local project audio path). Keep research URLs in `asset_origin`, not in a local asset slot. Use `music` only for a deliberate per-shot override. Keep extended source notes, composition treatment and the beat map in the narrative body. Decide the picture first and then how to obtain it; a planned source is not a completed asset.

The Studio script table edits this same file. Read its latest saved content before generation/apply; respect pinned visuals, music, effects and voices. Saving or reordering rows alone does not rebuild or retime the video. During generation/apply, synchronize composition and audio, matching existing frames by `src` rather than old row numbers. Add `src` only for a real built sub-composition; do not invent frame files or use the entire root video as every frame's source. Advance `outline` to `built` to `animated` only after the corresponding implementation exists. Inline voiceover is enough for short pieces; reuse `SCRIPT.md` when one exists or longer narration needs it. Do not maintain two independently edited transcripts. Update only affected frames after edits and replace estimated shot timing with measured narration/media timing before final assembly.

For a finished video, resolve the full-video music decision before assembly, even when the user leaves it to AI. Product introductions, explainers and promotional videos need a suitable instrumental music bed by default; narration is not a reason to omit it. Save a content-led `music_prompt` (mood, energy/pacing, instrumentation, vocals/no vocals, coverage and relationship to narration). Use exactly `music_prompt: none` only when the user requests no music or the approved script intentionally uses original sound only; explain why separately in notes. Never override a required soundtrack with an AI silence decision. Do not change a failed sourcing attempt to none to pass validation. A script-only request may leave assets pending; a finished soundtrack may not. Discover actual capabilities: speech synthesis is not music generation. Without a configured music generator, source a suitable licensed track and record its provenance; if neither route succeeds, report partial delivery, not completion.

Choose a suitable authorized track, not merely the first downloadable file. Compare a bounded shortlist against the direction, record title/source/license and a concrete fit rationale in script notes, then save its actual project-relative `music_asset` and mount that same file. Inspect/listen when supported; do not claim an audition that did not happen. Verify trim/loop coverage, supported fades and intelligibility beneath narration. If no suitable source is available, report partial delivery with the missing asset rather than pretending a planned soundtrack is complete.

Subject/fact corrections must propagate through affected script lines, actual spoken audio, rendered text, imagery and captions. Regenerate changed narration and retime affected clips; preserve unrelated user edits. Replacing a wrong picture with a logo while retaining obsolete narration is not a completed correction. A favicon is branding, not a substitute for requested product screenshots or explanatory material.

Do not call a video model merely to pan across a still. Preserve source evidence and label illustrative imagery. These choices feed the existing `artifact_media_review` plan in `brief.json`; the storyboard explains the story, while that host-owned record owns capability and asset outcomes. Do not duplicate generation-job state in the storyboard.

Keep publisher, source URL, date and attribution in `asset_origin` or frame notes. An article screenshot may establish the source when clearly identified; the article page URL itself is not an image/video file. Never present unrelated stock media or generated illustrations as footage of a real event. If suitable footage is unavailable, state the gap and choose a truthful treatment such as attributed source material, supported data or a clearly identified illustration. Research and media acquisition are allowed browser work; the host owns composition preview. Do not invent search capabilities, media URLs, licenses or successful downloads.

Shortlist at most three scene bodies and three mapped components; open only selected sources and relevant guidance. Video layouts describe spatial content slots, not complete compositions, timelines, narration or required scene duration. Match scale, framing, crop and pace to those changes. Avoid repeating the same entrance or camera treatment in every shot, and do not leave a static card unchanged through a long explanation. Transitions connect developed scenes; decorative loops do not replace development. A purposeful readable hold remains valid.

## Production order and Shotcraft selection

Default to recipe-first, not recipes-only. Try a fitting executable recipe, a compatible combination or a meaningful split before drawing custom graphics. When none preserves the required content, decide autonomously and document the considered recipes, exact semantic/input/capacity limitation, why combination or splitting does not solve it, and minimal custom scope in the frame narrative; mirror the reason in custom_reason and data-ipw-component-decision="custom:<specific reason>". No additional user approval is required unless the user explicitly prohibited customization. Convenience and decorative novelty are not gaps. Custom scenes receive the same narration alignment and rendered acceptance as recipe scenes; never claim they reused a recipe.

Keep selection visible in the same native frame metadata: recipe: <exact executable component ID> and scene_id: <exact installed scene ID>. Camera remains the movement instruction. For a custom frame, omit recipe and use custom_reason with its concrete rationale. After assembly reconcile these fields with actual mounted instances; preserve scene_id when reordering. The editor derives source-inspected mount status from index.html and existing recipe files; do not author a mounted/validated status or treat static mounting as rendered acceptance.

Use the pinned Shotcraft catalog through media/video_recipe_catalog. Search by the narrative need or category with bounded pages (limit <=20); read full rules through cardIds for at most three candidates. It includes all 157 cards and 214 preview variants, not 214 installable recipes. Each choice has suitability, energy, duration, exact card source, preview, implementation candidates, dependency imports and conversion state. A preview link is hosted upstream and can change; its last HTTP check is not an audition. Unresolved variant sources and placeholder/unverified converted HTML are reference-only. Only returned executable componentIds may be installed; read their local manifest and use its supported capacity and measured cue contract. Do not infer executable status from a card name, converted file count, or preview count. Under a recipes-only user request, an unsuitable library match needs another proven recipe, a meaningful split, or an explicit library-gap report, never custom graphics disguised as reuse.

### Sequence templates: compose recipes into a narrative

A sequence assigns narrative jobs, relative energy, reading rests and continuity to several shots; a recipe implements one job; a transition implements one boundary. A sequence is planning guidance, not an installable composition or proof that a listed recipe can execute. Choose a fitting sequence before detailed slot assignment, then reconcile it with the actual selected recipes. Keep the choice and justified changes in the first frame's existing notes, and each shot's slot and handoff in its narrative; do not add schema keys, pipe tables to STORYBOARD.md, or another planning file.

| Sequence | Choose when | Slots and rhythm | Reject or adapt when |
| --- | --- | --- | --- |
| promo-energy-arc | A short multi-feature product promotion needs a memorable reveal and close | Quiet identity/orientation -> one focal product subject -> distinct feature demonstrations alternating with readable rests -> a supported payoff or requested action | Not a universal explainer structure; a single-feature or very short film can merge slots. Never force a launch climax onto teaching or invent a CTA. |
| concept-to-application | Explain an unfamiliar term and help the audience recognize its use | Answerable question -> definition and boundary -> concrete example -> contrasting case or misconception -> practical takeaway; emphasis rises at the distinction, then settles | Not a mechanism simulation. Omit the contrast only when it adds no understanding; do not repeat the definition as every shot's headline. |
| mechanism-to-test | Explain why a process changes an outcome | Observable phenomenon -> supported ordered mechanism -> worked case -> test/prediction and its conditions -> resolution; stable framing through dependencies, rest after the mechanism | Do not turn correlation or an ordered list into causality. Feedback loops, branching and continuous simulations need genuinely supported recipes; text cards cannot stand in for those capabilities. |
| compare-to-decision | Compare two options against shared criteria | Common task and criteria -> paired evidence per criterion -> tradeoffs and limits -> conditional decision; keep comparison scale and reference points stable | Reject mismatched units, unrelated before/after views or an unsupported winner. Do not add dramatic opposing sides without an actual opposition. |
| task-to-outcome | Teach a real procedure | Goal and starting state -> dependent actions -> observable checkpoint -> resulting state -> recovery or next action when relevant; pauses at decisions rather than arbitrary chapter cards | Not a feature-benefit list. If true interface evidence is required, missing screenshots cannot be replaced with a fictional interface or decorative cards. |
| claim-to-evidence | Explain a factual or document-based claim | Context and question -> attributed evidence -> what it supports -> limitation or alternative explanation -> bounded conclusion; give the evidence its longest necessary reading interval | Do not treat generated illustrations, testimonials or source names as evidence. Preserve qualifiers; no mandatory celebratory finish. |

Only promo-energy-arc adapts the upstream sequence: [Video Shotcraft promo-energy-arc](https://github.com/Vincentwei1021/video-shotcraft/blob/main/references/sequences/promo-energy-arc.md), reviewed 2026-09-29, Copyright 2026 Wei Yihao, [Apache-2.0](https://github.com/Vincentwei1021/video-shotcraft/blob/main/LICENSE). Modified here for HyperFrames, content-led timing, executable local recipe slots and iPolloWork approval. The other five are iPolloWork planning patterns, not claimed Shotcraft ports. Retain attribution and the existing vendored Shotcraft license when redistributing this adaptation.

For a fitting 30–60s promotion, the upstream planning ranges are orientation 8–12%, focal subject 12–15%, feature development 55–65%, close 13–16%, with 2–4 optional breathing cards. These are observed starting points, not simultaneous fixed quotas: choose and normalize one allocation to the actual total, counting breath slots within it. Do not impose this budget on narrated teaching. Never copy upstream component names into executable selections: fill each slot only with a verified local recipe whose usage and capacity fit; report an unfillable required slot under recipes-only policy. A text-led local recipe does not acquire missing media, camera or mechanism capabilities through sequence membership.

#### Fill slots and budget time once

1. Choose one structure from the audience's task and source dependencies; combine only a necessary local sub-sequence, not every pattern. Assign each slot a takeaway, real input, executable recipe and observable landing state. Merge or omit optional slots with a reason; required facts and user constraints still control coverage.
2. During script drafting use rough positive shot durations and reserve necessary reading/rest windows before adding motion. Do not calculate frame-accurate budgets or word cues before synthesis, and do not repeatedly adjust prose to promotional percentages. A breathing slot can hold the current result or bridge to the next question; it need not be another title card, and must not repeat a tagline or become filler.
3. After approval and measured speech/media, convert the finalized slot windows to integer frames at project FPS. Every shot window covers Establish + Develop + Land; its incoming transition lives inside Establish, not as extra time or an overlapping scene. Respect the recipe's timing ratios and minimum hold. Count a spoken reading interval only once; a visual hold does not manufacture silence or justify shifting audio into an unrecorded pause. Extra silence requires actual supported audio handling and revalidation.
4. Allocate by semantic complexity and real reading time, not equal shares. Keep dense evidence/code readable and allow a resolved state to settle; if the budget cannot fit, split at a meaningful boundary or surface an explicit duration conflict. Update dependent captions, cues, music and SFX from the same final scene boundaries. No invented beat timestamps or parallel sequence timeline.

#### Design the handoff, then select a transition

For each adjacent pair, write one compact handoff in the incoming frame's existing narrative: the outgoing result -> continuation, comparison, topic/time/location change or closure -> the incoming subject -> what stays recognizable -> supported transition and its in-scene window. Example: a defined term lands; the next shot applies that same term to a real case, retaining its label and emphasis color; use a direct cut because the content establishes the connection. Keeping the concept recognizable does not require preserving the DOM node across subcompositions.

Preserve position, scale, comparison anchors or movement direction only where the installed recipes actually support them. If a desired object morph, shared camera path or cross-recipe motion is unsupported, use a truthful semantic handoff and cut, choose another verified pairing, or report the gap; never add custom graphics to imitate continuity. A topic change may deliberately reset the composition, but its intent must be clear.

Select at most one supported treatment per seam after the shot order is settled. A direct cut is valid. Do not replay an elaborate entrance at every handoff, stack multiple transitions, fade to an accidental empty frame, or cover a required final qualifier with the incoming effect. If entry motion already reveals the next subject, avoid a competing wrapper transition. Review the outgoing Land, boundary and incoming Establish together, plus the sequence's ordinary-speed rhythm, within the existing acceptance batch; naming a sequence does not establish success.

### Choose by narrative purpose, then verify the treatment

This selection method applies to native and imported recipes. Read concise catalog metadata first; shortlist at most three candidates, then read the chosen local recipe.md card, its manifest contract and actual implementation. Cards are generated from owning manifests by visual-component-catalog.ts recipe-cards-generate, not independently maintained rules. Installation carries the selected card into compositions/<componentId>.recipe.md and lists it in written paths. Before installation read only the shortlisted registry cards; afterward use the actual returned project-relative documentation path. If an older distribution lacks cards, read its manifest and disclose the missing documentation rather than inventing a path. For an imported treatment, resolve its exact card and variant, pinned reference implementation and preview. Compare the port with that reference where required; a similar name is not the same variant. Reuse reads for unchanged selections.

Filter candidates against five concrete constraints: the audience takeaway and visible change; available or obtainable authorized assets; supported content shape/capacity; narration or reading order and meaningful final hold; whole-video visual direction and relative energy. Reject any violated avoidWhen, missing essential input, or unsupported representation before considering visual appeal. Two options with shared criteria can use comparison-matrix; an evidenced linear causal mechanism can use cause-effect-chain, but an ordered list is not causality. Quiet code reading is not a reason for dramatic Dolly Zoom.

In each frame's existing narrative, keep one compact selection note: goal and visible change; chosen componentId (card/variant for imports); concrete fit rationale; required content/assets and known limits; one credible executable alternative with its tradeoff, or an honest no-fit reason; expected action/landing evidence. This is prose, not new storyboard metadata, a JSON sidecar, or an API field. Do not manufacture a backup when none fits. For example: compare two options on the same three criteria, choose comparison-matrix because paired rows remain aligned; an evidence-stack backup loses direct comparison and is rejected; inspect the spoken criterion's row and the final qualifier in the actual frames.

Before production, reconcile these notes with source coverage and the whole shot sequence. Every required takeaway needs a shot; adjacent shots must add information or preserve a purposeful continuity. Flag repetitive dominant treatments, missing rest, unjustified energy changes and explicit card usage-count violations. Do not import promo-wide once-per-effect quotas into teaching; obey actual recipe limits and user intent. Capacity overflow means a meaningful split or a different recipe, not truncation or smaller unreadable type.

For recipes-only work, set the existing root data-ipw-recipe-policy="recipes-only" during assembly and keep it through delivery. This user policy overrides any generic custom-scene fallback in older cards or template guidance: use another validated recipe, split without losing meaning, or report the library gap. Editable diagrams inside a real recipe are permitted; an original diagram disguised with a recipe label is not. Do not invent assets, discard required content, or silently switch to custom graphics to finish.

## Composition and timing

- Keep one authoritative root composition, its identity, declared stage dimensions and registered timeline. Use unique scene/clip IDs and supported editor hooks.
- Mark every full `.scene.clip` with `data-ipw-scene`. Its beat map uses scene-relative seconds, covers the complete scene without gaps or overlaps, and ends at the declared duration. Every beat binds stable `targets` to an executable `component:`, `preset:`, `custom:`, or explicit `hold:` animation reference. Keep full scene windows contiguous.
- Every scene after the first declares one incoming transition, duration, and narrative intent. Use a direct `cut` or an actual supported preset applied through `mutate_motion`; keep the returned `data-ipw-animation-reference`. Run the transition inside the incoming scene rather than overlapping full scene windows or fading the outgoing scene to empty.
- Keep mounted registry components host-timed. Preserve `data-ipw-timing-owner="host"` on the returned snippet, set the parent host to the actual scene duration, and let a completed component hold its Land state until that host ends. Never restore clip timing on the installed component root.
